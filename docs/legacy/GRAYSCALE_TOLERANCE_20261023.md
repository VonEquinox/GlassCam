# 灰度匹配与用户容差校准 · 2026-10-23

用户要求先使用主摄／超广角的灰度纹理匹配，再提供一个可直接调节的 Tolerance 滑条，以肉眼确定可接受差异，之后再将选定数字设为默认常量。本轮在 Mac 完成实现、原始输入重放和签名编译；未连接、安装、启动或调试手机。

## 手机上的校准方式

- 取景界面的“记录状态”上方显示“容差 / Tolerance”和两位小数。
- 范围 **0.25–4.00**，步长 **0.05**，初始值 **1.00**；向右更宽松。
- 设置立即用于后续当前帧检查，并在本机保存，重启仍保留。调节后需要让新帧完成检查与原有恢复过程，再评价画面。
- 每次按“记录状态”，原始双摄平面数据照常保留；按下时设置、分析设置、提交渲染设置及实际 GPU 纹理的设置分别保存，允许发现调节瞬间的旧结果。
- 找到可接受数值后，在同一场景分别保存“可接受”和“不可接受”的记录，再报告数字。最终固定默认值应依据用户选择；本轮没有擅自选定最终数值。

容差是匹配阈值的倍率，不是米、原生像素或直接指定透明度。1.00 对应原生接缝检查中的 3 个 192 宽分析像素的结构距离；NCC 下限 0.90。4.00 对应 12 分析像素、NCC 下限 0.60。平坦区域的残余亮度／颜色差、连续不支持结构的长度阈值也随倍率放宽。固定的真实像素覆盖、帧身份、时序和 200 ms 像素有效期保持独立；周期结构不能仅靠放宽相似度取得不存在的唯一位移。

## 与原版的差别

1. **灰度几何与显示颜色独立。** 主摄与超广角先按视场映射到重叠区域，灰度再进行亮度／对比度归一化。几何通过零偏移灰度相关及原生线条支持检查；有纹理区域不再因为 RGB 像素不同额外否决正确的纹理对应。最终外围仍显示原始彩色超广角数据，并使用独立估计的颜色参数。
2. **允许空间变化的修正。** 独立后台队列在 384 宽重叠区域及 32 像素真实超广角搜索边带上，尝试 Vision revision 1／2 的双向 veryHigh 光流。候选须经过前后向一致性检查；按实际灰度边缘一致性选择候选。光流只提供下一次检查的建议，不能自己认证显示，也不能延长旧图像的有效期。
3. **按外围边分别恢复。** 上／下／左／右各有原生证据、恢复策略、GPU 资源就绪状态和遮罩。某一接缝失败不再使另一条已验证接缝同时全黑。中央照片仍由原有预览显示。
4. **容差与 GPU 资源绑定。** 每个分析结果及纹理束携带实际使用的容差。滑条变化会重置显示证据与纹理缓存，保留昂贵的几何候选；新的设置不能直接放行旧设置检查过的纹理。晚到的上传回调仍须匹配纹理票据。
5. **弱纹理不过度放大噪声。** 两路灰度的分位区间均超过 0.05 才估计对比度倍率，否则只校正亮度中值。原先 0.005 的阈值会在微弱纹理上放大噪声，导致已对齐的场景被当成非平坦不一致区域。

原始主摄、超广角的完整视场并不相同；分析对照图是匹配所需的重叠裁切。`validation/second-field-20261023/raw-field-of-view.png` 保存了完整双路视场的对照，不能把重叠图当作两颗相机输出相同视角的证据。

- 原始记录：BGRA／10 位 YUV 原始平面、行尾字节、K／PTS、光流字段、容差值与 ZIP 校验通过。
- 全部 217 项 Python 回归通过；生产组件含 AddressSanitizer 检查通过。最终签名包、源文件指纹和日志索引见 `validation/second-field-20261023/verification.json`。

## 后续仍须判断

- 用户的可接受阈值必须通过手机实际图像选择；静态输入没有人工标注的透明度真值。
- 新场景、运动中的光流更新、系统玻璃最终叠加和手机算力／温度尚未由本轮离线测试证明。
- 原生检查会对无法取得完整支持的一条边整体拒绝；局部遮罩或其他匹配策略可以后续继续研究。不能把未知位移写成零以换取透明。
