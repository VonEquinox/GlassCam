# 文档写法

本仓库的文档只描述系统现在是什么样。做了什么、为什么改，交给 git 提交记录、`CHANGELOG.md` 和 ADR。

## 文档种类

| 种类 | 位置 | 内容 | 不写 |
|---|---|---|---|
| README | 仓库根目录 | 项目是什么、怎么构建、怎么测试、目录导览；一屏以内 | 进度、状态、测试数量、「最新」 |
| 架构 | `docs/architecture.md` | 分层、模块职责、依赖规则、从按快门到保存的数据流 | 历史方案 |
| 主题 | `docs/<主题>.md` | 一个子系统一篇：职责、工作方式、不变量、数据与版本、已知限制、代码入口 | 调查过程、某次运行的结果 |
| 决策 | `docs/adr/NNNN-标题.md` | 一个决定一篇：背景、决定、后果 | 实现步骤 |
| 变更 | `CHANGELOG.md` | 用户能感知的变化，一条一行 | 证据、测试过程、安装记录 |
| 术语 | `GLOSSARY.md` | 词义 | 行为和验收 |
| 来源与权利 | `NOTICE.md`、`vendor/*/ORIGIN.md` | 数据来源、版本、哈希、分发限制 | 实现说明、函数地址 |

调查记录、实验、性能测量、逆向分析和验证报告不进本仓库，放在 `GlassCam-research` 仓库。

## 规则

1. **原地更新。** 行为变了，就修改对应的主题文档。不新建带日期的文件；过时的内容直接删除，git 会保留历史。
2. **文档不是工作汇报。** 不写「本轮」「最新」「已修复」「已安装到手机」「未启动」「待验收」「N 项测试通过」。测试结果以测试命令的输出为准，安装和验收状态不属于仓库。
3. **限制只写一次。** 写在每篇末尾的「已知限制」里，一条一句。正文不加「不能宣称」「不等于」「不证明」之类的免责声明。
4. **不变量对得上测试。** 每条不变量写成一句可以验证的话，后面标注对应的测试，例如：`曝光只在解码前施加一次。— ImagingCoreTests/Exposure`。没有测试的约定，要么补测试，要么写进「已知限制」。
5. **数字只写设计参数。** 阈值、版本号、网格尺寸、默认值可以写；某次运行的耗时、误差、通过数量不写。
6. **只用仓库内的相对链接。** 不出现 `/Users/...`、`~/.codex/...` 这类本机路径。提到代码时指向文件或类型，不复制大段代码。
7. **写短。** 先写结论，一段只讲一件事。主题文档超过约 300 行就按子主题拆开。
8. **语言。** 正文用中文；代码标识符、命令、文件名、错误信息保持原文。术语以 `GLOSSARY.md` 为准。
9. **ADR 不改正文。** 被后来的决定替代时，只把状态改成「已被 NNNN 替代」。
10. **改行为就改文档。** 改变行为的提交必须同时更新相关主题文档，并在 `CHANGELOG.md` 加一行。纯重构不改文档。

## 主题文档模板

```markdown
# <子系统名>

两三句话：负责什么，不负责什么。

## 工作方式

数据从哪里来、经过哪些步骤、到哪里去。

## 不变量

1. <可以验证的一句话>。— `<测试名>`

## 数据与版本

持久化格式、版本号、旧数据如何迁移。

## 已知限制

- <一条一句>

## 代码入口

- `<路径或类型>`：<一句话>
```

## CHANGELOG 格式

```markdown
## 2026-10-28

- LUMIX：修复高饱和颜色回绕。
- 拍摄：Quality ProRAW 关闭 Apple 全局色调曲线。
```

## 改写示例

原文（README）：

> 2026-10-23 最新：根据两份故障分析修复证据聚合、纹理准备、质量恢复和 GPU 资源身份，并加入完整原生可见边界与每边光度模型。217 项回归、生产 Swift／Metal、AddressSanitizer、原始记录导出及签名 Release 检查通过；12 组实拍重放仍有 11 组未通过，未安装或连接手机。

改写后：

- `CHANGELOG.md`：`外围玻璃：修复显示链阻塞；增加可见接缝检查和逐边光度模型。`
- `docs/peripheral-glass.md` 的「已知限制」：`在多数已录制的实拍场景中，外围无法恢复到完全透明。`
- 测试数量、签名检查、是否连接手机：删除。
